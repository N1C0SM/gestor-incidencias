Gestor de Incidencias

Aplicación web (y app híbrida) para registrar, seguir y resolver las incidencias técnicas de un centro educativo: desde un proyector que no enciende hasta una licencia de software caducada. Proyecto de entrega del módulo DI 0488 del Ciclo Formativo de Grado Superior en Desarrollo de Aplicaciones Multiplataforma (DAM), construido con Angular 22 e Ionic 9.

La interfaz está en español, se adapta a escritorio y móvil y replica la maqueta de la entrega: cabecera oscura, tarjetas blancas con esquinas redondeadas, panel con gráfico de estados y barra de navegación inferior.

Aviso rápido: todos los usuarios, incidencias y actividad son datos ficticios y viven en memoria. No hay backend ni base de datos real. Consulta el aviso sobre los datos.

Repositorio: https://github.com/N1C0SM/gestor-incidencias · Documentación: https://n1c0sm.github.io/gestor-incidencias/

No hay una demo publicada en Internet: la aplicación se ejecuta en local siguiendo los pasos de Puesta en marcha.

Características

  • Acceso y registro: inicio de sesión con validación en vivo y cuentas de prueba, y registro de nuevas cuentas con comprobación asíncrona de que el correo no esté repetido.
  • Gestión de incidencias: alta guiada (título, categoría, prioridad y descripción), listado filtrable por estado y pantalla de detalle con el historial de fechas y el solicitante.
  • Permisos por rol: el usuario ve y exporta solo sus incidencias; el administrador ve las de todo el centro y puede cambiarlas de estado.
  • Panel de administración: cuatro tarjetas de resumen que filtran la tabla, gráfico de barras con Chart.js y actividad del sistema en tiempo real.
  • Informes: exportación a CSV (compatible con Excel) y a PDF maquetado, tanto del listado filtrado como de una incidencia concreta.
  • Ayuda integrada: manual de uso dentro de la propia aplicación, con credenciales de prueba, explicación de los estados y tabla de permisos.
  • PWA y app nativa: compilación de producción instalable con service worker y configuración de Capacitor lista para empaquetar la misma base de código en Android e iOS.
  • Accesibilidad: HTML semántico, jerarquía de encabezados, tablas con <caption> y scope, aria-live en los mensajes, enlace «saltar al contenido» y foco visible.

Puesta en marcha

Requisitos:

  • Node.js 22.22.3 o superior (también 24.15+ o 26+); el proyecto se ha desarrollado con Node 24.21 y npm 11.4.
  • npm 8 o superior (el proyecto fija npm 11.4.1 en package.json).
Example :
# 1. Instala las dependencias
npm install

# 2. Arranca el servidor de desarrollo
npm start

La aplicación queda disponible en http://localhost:4200. El servidor recarga la página automáticamente al guardar cambios.

Para compilar y comprobar tipos y plantillas antes de entregar:

Example :
# Compilación de producción; el resultado queda en www/
npm run build

# Compilación de desarrollo en modo vigilancia (sin optimizar)
npm run watch

La carpeta www/ es un sitio estático, pero el enrutado es de una SPA: al servirla hay que redirigir las rutas desconocidas a index.html.

Arquitectura de datos simulados

No hay backend. Toda la persistencia es una simulación didáctica en memoria que se inicializa desde src/app/core/data/seed.ts (3 usuarios, 12 incidencias y 3 eventos de actividad):

Example :
Páginas (standalone, OnPush)
   │ inject()
   ▼
AuthService ──► SqlService ──► seed.ts        (usuarios e incidencias)
   │               │
   │               └──► NosqlService           (feed de actividad, RxJS)
   │
   └──► localStorage («gi.sesion»)

Páginas ──► ExportService ──► jsPDF / CSV     (informes en el navegador)
  • SqlService simula una base de datos relacional con dos tablas, usuarios e incidencias. Todas sus operaciones devuelven Promise y esperan un retardo de 160 ms para que la interfaz tenga que gestionar estados de carga, como ocurriría con un servidor real. Devuelve copias defensivas de los registros y ordena las incidencias por código. Las altas nuevas reciben códigos correlativos a partir de INC-1013.
  • NosqlService representa una colección de documentos de solo lectura: el feed de actividad. Se implementa con un BehaviorSubject de RxJS (actividad$), de modo que cada cambio de estado o alta aparece al instante en el panel.
  • AuthService guarda la sesión en un signal (usuario, autenticado, esAdmin, nombre, iniciales, rutaInicio) y la refleja en localStorage para sobrevivir a una recarga. Las credenciales se validan contra SqlService.
  • ExportService genera el CSV (UTF-8 con BOM y separador ;) y los PDF con jsPDF y autoTable, directamente en el navegador.
  • NotificacionService centraliza los avisos emergentes de Ionic.

Consecuencia importante: los cambios no se persisten. Al recargar la página vuelven los datos de ejemplo; lo único que se conserva es la sesión iniciada, que se borra al cerrar sesión.

Calidad del código

  • Pruebas unitarias con Vitest y jsdom: 11 pruebas en 5 ficheros, que cubren SqlService (acceso, correo disponible, alta y estadísticas), AuthService (sesión en el signal y en el almacenamiento), ExportService (CSV y lista vacía), los guards de ruta y los validadores (emailExistsValidator y contrasenasCoinciden). Se ejecutan con:

    Example :
    npm run test:ci

  • ESLint 10 con angular-eslint: reglas de TypeScript y de accesibilidad de plantillas, prohibición de any explícito y de console.log (no-console). Se ejecuta con:

    Example :
    npm run lint

  • Prettier 3 para el formato (.prettierrc, 100 columnas y comillas simples) y TypeScript estricto (strict, strictTemplates, noImplicitReturns…), con presupuestos de tamaño en angular.json para avisar si el bundle crece.

  • Accesibilidad: estructura semántica, encabezados ordenados, tablas con <caption> y scope, textos alternativos y aria-live para los mensajes, foco visible y enlace «saltar al contenido». El objetivo es cumplir las pautas WCAG 2.1 AA.

  • PWA y rendimiento: la compilación de producción registra un service worker con ngsw-config.json, carga perezosa de las pantallas y fuentes del sistema (sin peticiones externas), por lo que la aplicación se puede auditar con Lighthouse.

Despliegue

Web (Vercel, Netlify o cualquier servidor estático)

  1. Compila en producción con npm run build; el resultado queda en www/.
  2. Publica www/ como sitio estático.
  3. Configura una reescritura de SPA: todas las rutas que no sean un fichero deben servir index.html. En Vercel basta con indicar npm run build como comando, www como directorio de salida y una reescritura de /(.*) a /index.html; en Netlify, un _redirects con /* /index.html 200.
  4. La PWA necesita HTTPS para que el service worker se registre (en localhost también funciona). En desarrollo el service worker está desactivado: solo se activa en la compilación de producción.

App nativa con Capacitor

El proyecto incluye las dependencias de Capacitor 8 y capacitor.config.ts ya configurado (appId es.nebrija.gestorincidencias, appName «Gestor de Incidencias» y webDir www):

Example :
npm run build          # genera www/ que consumirá Capacitor
npx cap add android    # solo la primera vez: crea el proyecto nativo
npx cap add ios        # solo la primera vez (requiere macOS y Xcode)
npm run cap:sync       # copia www/ y sincroniza los plugins
npm run cap:android    # abre Android Studio
npm run cap:ios        # abre Xcode

Las carpetas nativas (android/, ios/) se generan con cap add y no forman parte del código fuente de la aplicación web. Para iOS hace falta un Mac con Xcode; para Android, Android Studio con un SDK instalado. ionic.config.json declara el proyecto como standalone con integración de Capacitor.

Flujo de trabajo con Git

El proyecto se organiza con una adaptación de Git Flow, el modelo de ramas habitual para el trabajo en equipo:

  • main: entregas estables y etiquetadas (v1.0.0).
  • develop: rama de integración de las funcionalidades terminadas.
  • feature/*: una rama por pantalla o bloque de trabajo (feature/panel-dashboard, feature/alta-incidencias, feature/pantalla-ayuda…).
  • release/*: preparación de una entrega (solo correcciones y documentación).
  • hotfix/*: correcciones urgentes que nacen de main y vuelven a main y a develop.

Convenciones:

  • Commits con Conventional Commits y ámbito entre paréntesis: feat(incidencias): añade el alta con validación en vivo, fix(auth): corrige el guard de administrador, docs(readme): documenta los scripts, test(servicios): cubre el alta de incidencias.
  • Pull requests hacia develop con revisión de al menos otra persona y sin warnings de ESLint ni pruebas en rojo.
  • Etiquetas de versión (v1.0.0) en cada entrega.

Aviso sobre los datos

Todos los datos de la aplicación son ficticios. Los usuarios, las incidencias, las fechas y la actividad están inventados para el ejercicio y viven únicamente en memoria.

  • El estado inicial se carga en cada arranque desde src/app/core/data/seed.ts; la «base de datos» simulada de src/app/core/services/sql.service.ts no existe fuera del navegador.
  • No se envía ninguna información a un servidor ni se guarda en disco. Lo único que persiste es la sesión en localStorage (clave gi.sesion), y se borra al cerrar sesión.
  • Al recargar se pierden las cuentas registradas durante la sesión y los cambios de estado: vuelven las 3 cuentas y las 12 incidencias de ejemplo.
  • El proyecto no debe usarse con datos reales de personas ni del centro en su estado actual: es una simulación didáctica.

Las librerías de terceros utilizadas (Angular, Ionic, Chart.js, jsPDF, etc.) se distribuyen con licencias de código abierto (MIT en la mayoría de los casos); consulta el fichero package.json para ver el detalle de dependencias.
